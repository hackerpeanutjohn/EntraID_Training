# HITCON 2026 Entra ID Training 課程復盤

課程日期：2026-08-13

紀錄日期：2026-08-17

範圍：教材發布、Lab 環境、AI 助教與現場操作

> 這份不是成功案例，而是避免下次再踩同一個坑的操作紀錄。上課前直接照檢查清單跑一次。

## 下次上課先看這裡

- [ ] 學生區每個 Lab 都已公開，Notion Integration 也能讀到頁面與子頁。
- [ ] 複製或搬移 Notion 頁面後，重新檢查 Page ID 與 Integration 權限。
- [ ] 講師切換 Lab 只改變 AI 的預設值，不能限制 AI 只能查目前 Lab。
- [ ] 學生可以自行指定 Lab，也能詢問前面 Lab 的問題。
- [ ] 每個 Lab 至少用乾淨的 Docker 與 Codespaces 各跑一次。
- [ ] 教材中的指令必須實際貼進學生 container 驗證，不能只看語法覺得合理。
- [ ] Docker、Codespaces、教材檔案與解密流程都準備一條最短備援路徑。
- [ ] 課前用歷史問題跑 AI 驗收，明顯失準超過 10% 就不要開放。
- [ ] AI 回答必須顯示採用的 Lab 與來源頁面，找不到依據就先追問。
- [ ] 課後再清除 log、撤銷課程帳號與短期憑證，不要在課程進行中阻擋學生貼完整錯誤。

## 這次發生了什麼？

AI 助教共留下 29 次互動、11 個 session。人工逐題複核後：

| 品質 | 次數 | 比例 |
| --- | ---: | ---: |
| 明確良好 | 7 | 24.1% |
| 部分可用 | 10 | 34.5% |
| 明顯失準 | 12 | 41.4% |

回答時間中位數約 16 秒，速度不算主要問題。真正麻煩的是回答方向錯誤。技術實作課只要給錯一條指令，學生可能多繞十幾分鐘，講師最後還是得親自救火。

## 最大的失誤：Lab 沒有同步

29 題裡有 22 題被系統歸在 Lab 0，但不少問題其實已經在問 Lab 1 或後面的 token、FOCI、MFA 與 Azure 操作。

當時的設計把講師設定的 current Lab 當成唯一檢索範圍。現場只要發生以下情況，AI 就會拿錯教材：

- 講師已經進到下一個 Lab，後台仍停在前一個 Lab。
- 學生進度比較慢，回頭詢問前面的步驟。
- 學生提早完成，開始詢問後面的內容。
- 一個問題同時牽涉前後兩個 Lab。

下次的規則應該很簡單：

> current Lab 只是預設值，不是硬限制。AI 要從學生指定的 Lab、目前目錄、指令與錯誤內容判斷情境。不確定就先問，不要硬猜。

## AI 助教還踩了哪些坑？

### 找不到教材時仍然亂補

檢索沒有命中正確內容時，模型仍嘗試產生完整答案，結果出現錯誤 Docker 建議、錯誤 token 解讀、無關 API 與虛構來源。

下次要把規則寫死：

- 技術結論必須附教材頁或核准的官方來源。
- 找不到來源時，不得新增指令。
- 信心不足時，只問最少的必要資訊。
- 回答畫面要顯示它目前判定的 Lab。

### 沒有穩定判斷執行環境

學生可能在 macOS、Windows PowerShell、WSL、Codespaces、Docker host 或 workstation container。這些畫面看起來都像 Terminal，但路徑與可用指令完全不同。

曾發生學生已在 container 的 `/workspace`，AI 卻叫他回 host 的 Downloads 目錄。下次收到問題時，至少先判斷：

1. Prompt 顯示的使用者與 hostname 是什麼？
2. `pwd` 在哪裡？
3. 目前有沒有 `docker` 指令？
4. 這條指令應該在 host 還是 container 執行？

### 回答太長

學生卡住時不需要一篇文章。他需要知道現在發生什麼，以及下一條要貼什麼。

下次固定使用四段格式：

1. 判斷：最可能的原因。
2. 操作：只給一個下一步。
3. 預期：成功與失敗會看到什麼。
4. 回報：失敗時要貼回哪一段輸出。

### 沒有先做離線驗收

模型、prompt、Notion 與 tool call 看起來都能運作，不代表適合直接放進教室。這次最可惜的是沒有先拿真實問題做固定測試。

目前的 29 題應保留為 regression test。下次修改教材、prompt、檢索或模型後，都要先重跑一次。最低標準如下：

- 明顯失準低於 10%。
- 不得虛構來源或指令。
- 不得出現內部思考文字。
- Lab 判斷不明時必須追問。
- 問題與教材不符時，要能明確告訴學生找不到依據。

## 教材與 Notion 的問題

課程同時有導師區與學生區，部分頁面使用複製，部分頁面直接搬移。這會帶來兩種風險：

- 搬移後 Page ID 或父層關係改變，AI 仍使用舊的頁面設定。
- 新頁面沒有分享給 Notion Integration，API 直接回 `object_not_found`。

教材發布不要靠記憶。每次移動或複製頁面後，執行同步檢查：

- 學生本人能否開啟。
- Integration 能否讀取。
- 子頁是否一起被讀取。
- AI 回答引用的網址是否真的存在。
- 舊頁面是否還殘留在設定中。

如果課程要逐步揭露內容，建議保留穩定的學生頁面，不要在上課時搬動來源頁。可以改成切換可見狀態或同步內容，避免 Page ID 一直變。

## Lab 指令的問題

這次有幾段 roadtx、device registration、PRT 與 Graph 查詢指令，光看文件時合理，實際進入學生 Docker 環境才發現 CLI 版本、參數與 token resource 不一致。

下次每個 Lab 都要做三層驗證：

1. 從全新的學生環境開始，不沿用講師機器的 token 或檔案。
2. 完整複製教材指令，不在腦中自動修正。
3. 同時驗證成功路徑與預期失敗路徑，確認錯誤訊息與教材敘述一致。

尤其是 identity Lab，必須把「裝置註冊成功」「取得 PRT」「代表使用者取得 resource token」分開驗證。三者不是同一件事，教材也不能混在一起寫。

## 環境備援怎麼準備？

Docker Desktop 可以保留，因為不少學生仍能現場安裝。Codespaces 則是公司電腦無法安裝 Docker 時的第一備援。

上課前要完成：

- Repo 在指定時間可讓學生建立 Codespace。
- devcontainer 與 compose 在新帳號上可正常啟動。
- 加密教材檔案能在 Codespaces 內解密。
- 學生不需要額外安裝 CLI 才能開始 Lab 0。
- 一頁 onboarding 足以讓學生自行完成，不需要講師逐台操作。

備援方案不是放一個連結就算完成。至少要找一個沒參與教材製作的人，照學生頁面從零操作一次。

## 上課當天怎麼操作？

### 開課前 30 分鐘

- 從學生帳號開啟所有已公開頁面。
- 建立一個全新的 Codespace。
- 從乾淨環境啟動 Docker Lab。
- 問 AI 三題目前 Lab、前一個 Lab、錯誤 Lab 的問題。
- 確認 AI 顯示的 Lab 與引用來源正確。

### 每次切換 Lab

- 先發布學生教材。
- 確認 Notion Integration 已讀到新內容。
- 更新 AI 的預設 Lab。
- 用一題 smoke test 確認來源。
- 再告訴學生開始操作。

### 學生貼問題時

- 保留完整指令、錯誤與 prompt，這些資訊對判斷環境很重要。
- 允許短期課程 secret 出現在私有助教系統，但不要寫入公開 GitHub。
- 如果 AI 的第一個判斷不合理，立刻停用該 Lab 的自動回答，不要讓錯誤答案繼續擴散。
- 現場修正後，同步更新該 Lab 指引或全域指引。

### 課程結束後

- 下架 AI 與臨時公開入口。
- 撤銷課程帳號、API key、client secret 與其他短期憑證。
- 匯出並去識別化互動紀錄。
- 把新問題加入 regression test。
- 更新這份復盤，不要等到下一次備課才回想。

## 下一版 AI 助教怎麼定位？

先不要追求一個什麼都會的 Agent。一天的實作課更需要一個穩定的「log 判讀＋教材導航」工具。

建議下一版只做三件事：

1. 判斷學生在哪個 Lab 與哪種執行環境。
2. 找到對應教材與官方來源。
3. 給一個可以驗證的下一步。

低成本模型負責分類與簡單解釋。只有教材已命中，而且確實需要跨步推理時，才交給較強模型。這比直接開一堆 tool call 更便宜，也更可靠。

## 這次真正學到什麼？

這次不是完全失敗。學生確實願意把畫面、log 與操作問題交給 AI，代表需求存在。失敗的是我們把「系統有回答」誤認成「回答能幫學生繼續前進」。

下次要驗收的不是 chatbot 有沒有動，而是學生拿到答案後，有沒有更快完成眼前這一步。
